## 🔴 CRITICAL

### C1. `resetReceived()` может НАВСЕГДА отключить приём RF — ворота перестают открываться
**`src/CC1101Manager.cpp:1291`, `src/main.cpp:1656`, `src/main.cpp:967`**

`checkReceived()` перед `return true` уже переподключил прерывание (CC1101Manager.cpp:1272-1274), т.е. во время обработки ключа в `loop()` приём снова активен. Между этим и вызовом `resetReceived()` выполняются долгие операции: `sendWebSocketEvent()`, `sendLog()`, `saveSystemState()` c `nvs_commit` во flash (десятки мс). При зажатой кнопке брелок шлёт кадры непрерывно (~30-50 мс), поэтому ISR успевает принять следующий пакет, выставить флаги и вызвать `detachRawInterrupt()`. Затем `resetReceived()` **без критической секции** обнуляет `receivedFlag`/`rawSignalReady`, но **не переподключает прерывание**. Путей восстановления нет: `attachRawInterrupt()` вызывается только внутри `checkReceived()` (за guard `if(!receivedFlag||!rawSignalReady) return`, флаги только что стёрты) и в `enterRawReceive()` (только при смене частоты/`init`).

**Отказ:** пользователь держит кнопку → приём мёртв до смены частоты через API или ребута, без сообщений об ошибке. Плюс `rawSignalIndex=0` посреди захвата и `lastInterruptTime=0` без сброса `firstEdgeCaptured` (следующая delta = `micros()-0` трактуется как конец пакета).

### C2. Нет аутентификации на управлении + захардкоженный пароль AP — любой в радиусе Wi-Fi открывает ворота
**`src/main.cpp:1376` (и все `server.on`), `src/main.cpp:1300`**

Ни один `server.on(...)` не проверяет токен/сессию (grep по auth/token/session — пусто). `/api/gate/trigger` безусловно вызывает `triggerGatePulse(500)`, минуя всю логику `isKeyMatch`. При этом `setup()` **всегда** поднимает `WiFi.softAP("SmartGate-Config", "12345678")` — пароль-литерал, не меняется через API. Те же открытые эндпоинты дают вход в обучение (`/api/keys/learn`), удаление/добавление ключей, смену частоты, перезапись Wi-Fi-кредов.

**Отказ:** атакующий во дворе подключается к AP по паролю `12345678` → `POST /api/gate/trigger` → ворота открыты без брелока. Прямой физический вектор; в «Известных ограничениях» это НЕ значится как принятое решение.

**Смежное (CSRF, high):** отсутствие CSRF-токена/кастомных заголовков — любой сайт в браузере жертвы (в той же сети) может сделать POST на `/api/gate/trigger`.

## 🟠 HIGH

### H1. `isKeyMatch` слишком мягкий — чужой брелок открывает ворота
**`src/main.cpp:501` (ветка 4) и `src/main.cpp:484` (ветка 3)**

- **Ветка 4 (стр. 496-511):** ключи считаются совпавшими, если короткая `bitString` — префикс ИЛИ суффикс длинной, минимум всего **12 бит**, **без проверки протокола**. TE-проверка пропускается, если `saved.te==0` или `receivedTe==0` (а `lastKey.te` может быть 0). 12 бит = 4096 комбинаций, преамбулы общие у брелоков одного бренда.
- **Ветка 3 (стр. 484-491):** совпадение по `saved.code == received.code` **без учёта bitLength и протокола** (`code` — младшие 32 бита; 12-бит `0xABC` == 24-бит `0x000ABC`). Комментарий на стр. 482 прямо говорит «протокол может быть другим!».

**Отказ:** сохранён CAME 12-бит `0xABC` → чужой Nice/Princeton 24-бит с `0x000ABC` и TE в ±40% → `return true` → ворота открыты посторонним пультом другого протокола.

### H2. `verifyKeySignal()` нигде не вызывается — ворота открываются с первого же кадра
**`src/main.cpp:1598` (определение — 519, объявление — 179)**

Функция адаптивной верификации по N повторам определена, но **не вызывается ни разу** (grep). В радио-пути при `keyExists && enabled` реле дёргается немедленно после `isKeyMatch` (комментарий стр. 1589: «активируем сразу... как Flipper»). CLAUDE.md утверждает обратное. Спроектированный слой защиты от единичного ложного декода полностью обойдён — усиливает H1: достаточно ОДНОГО ошибочно совпавшего кадра.

### H3. Настройки CC1101 из NVS никогда не применяются после перезагрузки
**`src/main.cpp:811`**

`loadSystemState()` читает `bitRate/freqDeviation/rxBandwidth/outputPower` из userdata, но в `setup()` к радио применяется **только частота** (стр. 1269). `setBitRate/setRxBandwidth/setFrequencyDeviation` вызываются лишь в `handleCC1101Settings`. `outputPower` не применяется к железу нигде. Дефолты `3.79f/58.0f` — старая конфигурация, не совпадает с реальной `init()` (20 kbps/135 кГц).

**Отказ:** пользователь ставит `rxBandwidth=270кГц`, приём работает → после ребута радио снова 135 кГц, брелок не открывает ворота, а UI показывает 270 кГц — по интерфейсу причину не найти.

### H4. `/api/wifi/connect` пишет креды в NVS ДО подключения и не проверяет ошибку парсинга
**`src/main.cpp:270`, `src/main.cpp:276`**

`deserializeJson(doc, server.arg("plain"))` без проверки `DeserializationError`. При пустом/битом теле `ssid/password` становятся `""`, затем `systemState` безусловно перезаписывается и сразу `saveSystemState()` — до `WiFi.begin()` и независимо от результата. Ветка ошибки подключения (305-310) ничего не откатывает.

**Отказ:** `POST /api/wifi/connect` с телом `{}` → валидные креды роутера стёрты в userdata → после ребута контроллер не подключится к домашней сети (останется только AP).

### H5. Тело запроса буферизуется в RAM без лимита размера — DoS
**`src/main.cpp:848` (и 270, 878, 912, 1008, 1033, 1124, 1178)**

`server.arg("plain")` читает всё тело в String на куче; ESP32 WebServer берёт `Content-Length` без верхней границы. Свободной кучи ~250-300 КБ.

**Отказ:** неаутентифицированный `POST /api/phones` с телом ~500 КБ → OOM → reset ESP32. Повторяемо любым клиентом.

### H6. Декодер Nice FLO не декодирует ни одного бита (мёртв)
**`include/protocols/ProtoNiceFlo.h:38`**

Фазы state machine рассогласованы: `FoundStart` сохраняет HIGH и переходит в `CheckDur`, но `CheckDur` ждёт снова `if(level)` (HIGH), а после HIGH всегда идёт LOW → ветка `else state=Reset`. `SaveDur` (`if(!level)`) недостижим. У рабочих декодеров (CAME/Princeton) пара бита: `SaveDur` ловит HIGH, `CheckDur` ловит LOW.

**Отказ:** любой пульт Nice FLO нельзя ни обучить, ни распознать.

## 🟡 MEDIUM

### Декодеры
- **`CC1101Manager.cpp:887` — `data_2` игнорируется + UB-сдвиг для >64 бит.** Верхние биты длинных протоколов (Nice One 72б, Alutech 72б, KingGates 89б, Somfy Keytis 80б) лежат в `data_2`, который в `checkReceived` не читается. Цикл `dr.data >> b` при `b>=64` — UB (на ESP32 маскируется mod 64). `bitString` для >64-битных ключей строится неверно → обученный ключ никогда не совпадёт.
- **`CC1101Manager.cpp:877` — нет `resetAll()` между буферами.** `feed()` сбрасывает декодеры только при победе. Если за буфер никто не выдал `ready` (частый RAW/Unknown), state machine сохраняют накопленные биты и дописывают импульсы из следующей посылки → возможна «химера» из двух пакетов, способная совпасть с обученным ключом.
- **`ProtoGateTx.h:187` — ProtoChamberlain никогда не эмитит.** Единственный `emitResult` в `SaveDur.else` (требует HIGH), но туда всегда приходит LOW; `CheckDur` на несовпадении делает голый `else state=Reset` без emit. 9 накопленных бит никогда не выдаются.
- **`ProtoBatch3.h:20` — ProtoHoltekHT12X мёртв.** `FoundStart` проверяет `if(!level)` сразу после LOW-преамбулы, но следующий импульс всегда HIGH → вечный Reset. Копипаст-баг: у корректного `ProtoHoltek` (ProtoGateTx.h:78) — `if(level && ...)`.
- **`ProtoBatch2.h:162` — ProtoLegrand теряет половину кодов.** `FirstBit` требует короткий первый HIGH; кадры, где первый бит кодируется длинным HIGH (бит '0'), отбрасываются. В референсе Flipper `LegrandDecoderStepFirstBit` принимает оба варианта.

### Персистентность / логика
- **`main.cpp:425` — `saveSystemState()` не проверяет `doc.overflowed()`.** В ArduinoJson 7 при нехватке heap `add()` молча пропускается, `serializeJson` выдаёт валидный, но неполный JSON → усечённое состояние перезаписывает полное (нет бэкапа/транзакции) → перманентная потеря части ключей.
- **`main.cpp:738` — `loadSystemState()` игнорирует ошибку `deserializeJson`.** Повреждённый blob молча → пустое состояние → перезаписывается пустым.
- **`main.cpp:1529` — ошибка записи NVS при обучении не всплывает.** Ключ остаётся только в RAM, UI сообщает об успехе.
- **`main.cpp:1599` — полная сериализация всего state-blob на КАЖДУЮ активацию ворот (`gateOpenCount++`).** Износ flash + блокировка приёмного цикла на время `nvs_commit`.
- **`main.cpp:287` — блокирующий `delay` до 10 c в `handleWiFiConnect`.** Весь `loop()` замирает: приём RF, WebSocket, остальные HTTP.

### Сеть / вывод
- **`main.cpp:210-216` — WS-JSON собирается конкатенацией без экранирования.** Кавычка в имени ключа/SSID/номере ломает `JSON.parse` на фронтенде (события молча теряются); потенциальный XSS-вектор.

- **`main.cpp:31 (GPIO12)` — реле на strapping-пине MTDI.** Задаёт напряжение flash при загрузке; подтяжка реле может мешать старту.

### ⏸️ Намеренно НЕ трогал (нужна проверка на железе / принят риск)
- **H1 `isKeyMatch` / H2 `verifyKeySignal`** — «мягкое» сравнение (12-бит префикс, code без протокола) и immediate-trigger. Ужесточение/включение верификации рискует перестать узнавать реальные CAME/Nero/Keeloq из-за нестабильности имени 24-бит протокола (см. lessons.md). Плюс это security-грань, которую просили пропустить. Чинить с пультами в руках.
- **Мёртвые декодеры Nice FLO / HT12X / Legrand** — подтверждённо мёртвы (инверсия фаз state machine), но включение даёт риск ложных срабатываний против реальных протоколов (Nice FLO стоит 4-м в цепочке — жадный матч затенил бы Nero/Keeloq/Princeton), а проверить без эфира нельзя. Фикс — по одному протоколу с контролируемым TX Flipper.
- **Chamberlain** — физически не принимается: преамбула 39 мс > порога конца пакета в ISR (`MAX_PULSE_US=30000`). Фикс декодера бесполезен без правки ISR (рискованно для CAME/Nice).
- **`resetAll()` между буферами** — межбуферное состояние намеренно нужно Nero Radio (реальный протокол пользователя); слепой сброс регрессировал бы Nero. «Химера» из двух пакетов — редкий теоретический случай.
- **Блокирующий `delay` в handleWiFiConnect/setup** — синхронный `WebServer` не даёт чисто асинхронный ответ; блокировка идёт только на явно инициированное пользователем подключение.
